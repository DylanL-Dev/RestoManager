Mission lancée par « D’accord go », après validation du portail RM-015.1. Départ DEV `6ec2f01`, sauvegarde distante `backup/rm0152-dev-before-20261118`, branche `feature/rm015-secure-booking`. Aucune autorisation V3/MAIN/PROD.

## Règles confirmées

- Nombre maximal choisi par chaque Restaurant, sans quota Web distinct à cette étape.
- Planning partagé et pourcentage de répartition des arrivées configuré dans Gestion. Le plafond d’arrivées devient bloquant pour le Web ; les dérogations salariées existantes restent disponibles.
- Une à trois personnes : confirmation après validation atomique. Quatre et plus : demande à confirmer par Restaurant.
- Délai de validation **une heure**, confirmé par le propriétaire ; réglable dans Gestion.
- Indicateur par créneau : Disponible / Dernières disponibilités / Complet, calculé pour le groupe. Aucun compteur brut de sièges.
- Emails préparés et testés, **sans activation ni envoi externe**, à la demande du propriétaire.
- Migrations testées sur une base éphémère ; impacts présentés avant toute application à une base partagée.

## Points de partage

Le verrou `restaurant-mutation-v1:{restaurant_id}` précède toute mutation Web, comme les RPC salariées. Les propositions réutilisent `private.ranked_booking_sets`, donc les capacités et fusions autorisées existantes. Une vérification explicite exclut aussi les tables encore installées, y compris depuis la veille. Les maintiens Web sont des maintiens de la table existante `table_holds`, avec propriétaire Web distinct, sans créer de compte Auth ou usurper un salarié. Ils sont donc visibles dans les snapshots, empêchent les réservations concurrentes et bloquent la clôture RM-012 jusqu’à leur expiration.

Le schéma prévoit un lien privé entre maintien et demande Web. Les maintiens salariés conservent un utilisateur ; les maintiens Web ont un identifiant privé de demande et aucun utilisateur. Une contrainte impose strictement ces deux formes. Les comparaisons d’identité de maintien deviennent null-safe (`IS DISTINCT FROM`) dans les fonctions concernées : un maintien Web ne peut être considéré comme libre par une ancienne fonction salariée.

La résolution du tenant accepte le contexte d’une API uniquement lorsque le rôle PostgreSQL appelant est réellement `service_role` et qu’aucun utilisateur n’est connecté. Ce rôle est déjà privilégié ; aucun élargissement `anon` ou `authenticated`. Le rôle salarié demeure nul pour le Web, les RPC réservées aux employés restent refusées. Le propriétaire des nouvelles fonctions n’est ni propriétaire de tables ni BYPASSRLS ; les politiques imposent le tenant de chaque requête.

Une API publique sans compte filtre les entrées et réponses, masque les identifiants des tables, applique les limites anti-abus et appelle exclusivement des RPC réservées au backend. Jetons opaques aléatoires de 256 bits, empreintes en base, expiration/révocation, version et clés d’idempotence. Le jeton nécessaire aux emails est chiffré côté serveur avant stockage ; sa clé reste dans les secrets d’environnement.

La modification d’une réservation confirmée conserve la réservation initiale tant que la nouvelle proposition n’est pas validée. Pour quatre personnes ou plus, le maintien temporaire de la proposition n’annule pas l’ancienne réservation ; rejet ou expiration la conserve. Une intervention salariée prime et invalide la proposition périmée.

La production et le portail de démonstration restent séparés. L’entrée de recette serveur reste désactivée tant que migration, URL API, secrets, mentions officielles et paramètres du Restaurant ne sont pas validés. Aucun repli vers une confirmation locale fictive n’est permis dans l’entrée réelle.
