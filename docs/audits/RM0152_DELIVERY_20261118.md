# RM-015.2 — Réservation publique sécurisée

## Résultat et périmètre

Le portail RM-015.1 est complété par un parcours relié au serveur, un moteur transactionnel réutilisant les tables et les arrivées existantes, et un suivi Restaurant. Le délai retenu pour les demandes de quatre personnes ou plus est **une heure**, réglable. Les emails sont préparés mais désactivés, conformément à la réponse du propriétaire.

Branche `feature/rm015-secure-booking`, issue de DEV `6ec2f01`. Sauvegarde distante `backup/rm0152-dev-before-20261118`. Livraison vers DEV uniquement. MAIN et RestoManager-V3 conservent respectivement `aab5454b` et `17646fea`. Aucun appel d’écriture à une base Supabase partagée, aucune réservation fictive réelle, aucun email externe.

La connexion publique partagée reste fermée jusqu’à validation des [impacts et de la procédure d’activation](RM0152_ACTIVATION_DEV_20261118.md). Les captures connectées proviennent de l’API locale et de PostgreSQL réel **éphémère**, pas d’un enregistrement local fictivement présenté comme confirmé par le serveur.

## Fonctionnalités

- Le Restaurant choisit le maximum, le délai, l’horizon et les conditions du portail. Aucun changement automatique des horaires ou du pourcentage d’arrivées.
- Les créneaux affichent Disponible, Dernières disponibilités ou Complet pour le groupe demandé, sans compteur trompeur de sièges.
- Les tables encore installées bloquent le Web même si l’heure prévue de départ est passée. Aucune libération ni absence inférée.
- Le maintien Web utilise la même table `table_holds` que les salariés. Il bloque une réservation concurrente, apparaît dans le snapshot et entre dans les vérifications RM-012.
- Les petits groupes sont confirmés après la dernière vérification. Les groupes d’au moins quatre personnes attendent une décision Restaurant avant l’échéance. Refuser ou expirer ne crée pas de réservation.
- Les demandes de modification de groupe gardent l’ancienne réservation. Un refus, une expiration ou une intervention salariée rétablit le récapitulatif actuel, sans exposer les notes internes. La demande particulière du client est conservée séparément et remplacée lors d’une modification, sans s’accumuler dans les notes internes.
- Le client consulte, modifie ou annule avec son seul lien, dans les limites prévues. Fermer le canal Web n’invalide pas ces liens existants.
- La source RM-014 regroupe chaque demande en une alerte non retirable tant qu’elle attend une décision. La lecture ne confirme pas le groupe. Une erreur de synchronisation est signalée.
- La saisie des réglages résiste aux rafraîchissements. Le renouvellement de l’application attend la fin d’une action et protège les brouillons RM-011.

## Recette et limites

Avant activation, le clone Render conserve la démonstration accessible à `/reservation/?restaurant=a-lepicerie-rouen`. La nouvelle entrée `/reservation/live.html?restaurant=a-lepicerie-rouen` explique que les réservations connectées ne sont pas encore ouvertes ; elle ne simule pas une réussite. Gestion indique que le module attend son contrat serveur lorsque la migration n’est pas installée.

Pour reproduire la recette connectée sans données réelles : `npm ci`, installation de Chromium Playwright, Docker local, puis `npm run test:public-connected:postgres` et `npm run test:public-connected:browser`. Les fixtures démarrent et détruisent leur base ; il n’y a aucun paramètre autorisant une URL de base distante. Le workflow CI exécute cette même validation et conserve les artefacts.

Avant ouverture partagée : valider les impacts de migration, vérifier le projet DEV, configurer l’Edge et les origines, renseigner les mentions du Restaurant, garder les emails désactivés et respecter la procédure liée en début de rapport. Les captures ne prouvent pas une exécution d’Edge sur le réseau Supabase réel : l’entrée est vérifiée par Deno, le handler et SQL tournent localement. La configuration du proxy, la délivrabilité et la charge distribuée restent à vérifier lors de l’activation. Le challenge progressif échoue fermé sans fournisseur configuré ; son widget interactif reste à raccorder avant une large ouverture publique. La conservation automatisée des données et l’envoi d’emails nécessitent également une configuration validée.

Aucune anomalie bloquante connue dans les scénarios validés. Ces essais automatisés ne constituent ni une étude avec de vrais clients/employés, ni une certification d’accessibilité. Aucune publication officielle n’est effectuée.
